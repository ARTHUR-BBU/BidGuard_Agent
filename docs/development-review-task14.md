# BidGuard Task 14 阶段复盘：给后台闭环装上用户看得懂的工作台

> 文档性质：开发记录与能力边界说明，不是营销承诺。
>
> 当前范围：类型化前端 API 客户端、状态徽标、应用壳层与基础路由。

## 1. 先给结论

Task 13 让后端可以记录人工决定、保留历史，并在材料变化后按影响范围重新核查。Task 14 把这套后端能力第一次放到用户面前：现在有了 BidGuard 的正式工作台入口、统一导航、统一状态语言和后续页面地址。

它还不是完整的前端业务流程，而是后续页面不会迷路的“地图和门牌”。

## 2. 为什么必须有 Task 14

如果没有前端工作台，后台就像一间有档案、流程和员工的办公室，但没有前台：用户不知道从哪里开始，也不知道“待补充”和“待确认”有什么区别。

Task 14 先把道路、门牌和仪表盘统一起来，避免 Task 15–17 各自写一套导航或重新解释后台状态。

## 3. 它在整体开发地图中的位置

```text
Task 11：按规则运行审核 Agent
        ↓
Task 12：任务可排队、可恢复、可查状态
        ↓
Task 13：人工决定 + 行动项 + 版本影响复核
        ↓
Task 14：前端工作台骨架 ← 本次
        ↓
Task 15：创建项目、上传材料
Task 16：审核总览、逐条矩阵
Task 17：问题详情、人工处理
```

## 4. 本次真正落地的能力

- `DisplayStatus` 严格复用后端五种状态：高风险、待补充、可优化、已满足、待确认；
- `StatusBadge` 同时显示文字、颜色和小圆点，不能只靠颜色区分；
- `ApiError` 统一保留 HTTP 状态、错误码和用户可读消息；
- API 客户端支持 JSON 和 `FormData`，不把 API key 放进浏览器；
- 建立 `/projects`、`/projects/new`、`/projects/:id/review`、`/requirements/:id`、`/evidence` 路由；
- 桌面端使用克制的侧边栏，窄屏切换为可横向滚动的顶部导航。

## 5. 用户实际得到什么

```text
打开 BidGuard
    ↓
看到“新建核查 / 投标项目 / 企业资料库”三个入口
    ↓
进入项目、审核、要求详情或资料库的固定地址
    ↓
用统一中文状态理解后台返回结果
```

## 6. 验收证据

- Vitest：2 个测试文件、6 项通过（状态徽标 5 项，应用导航 1 项）；
- `npm run lint`：通过；
- `npm run build`：通过；
- 变更限制在前端壳层、类型化 API 客户端、测试和文档；
- Task 14 分支提交前不会触碰真实后端数据库或业务材料。

## 7. 仍然没有完成的内容

- 没有项目创建和文件上传；
- 没有真实项目列表、审核矩阵和后台轮询；
- 没有问题详情页的人工作决定提交；
- 没有报告导出，也没有真实业务语料上的前端可用性验证；
- 当前“后台连接待配置”是诚实的占位状态，不代表后端已经接通。

## 8. 下一步因果链

Task 14 已经给后续功能准备好固定入口，但页面还没有真实业务数据。因此下一步进入 Task 15：实现项目创建、招标/投标文件上传和企业资料选择，并让提交按钮只在必需材料齐全时可用。
