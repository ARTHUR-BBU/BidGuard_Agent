# BidGuard Agent 产品与技术设计

- 日期：2026-09-16
- 状态：已完成逐段确认，等待用户复核书面版本
- 产品阶段：学习型 MVP，同时保留垂直收费产品的发展路径
- 目标行业：政府采购与企业招标
- 初始客户：参与投标的中小型软件与 IT 服务公司

## 1. 产品结论

BidGuard Agent 是一个提交前投标文件核查工具。它读取招标文件、投标初稿和企业资料，建立可追溯的要求矩阵，分别发现：

1. 可能导致无效投标的资格、格式、商务和实质性响应风险；
2. 可能导致评分损失的证据不足、响应不完整和可优化项。

产品不承诺中标，不代替企业作出事实承诺，也不直接向采购平台提交材料。它的角色是投标团队的“提交前质量门”，帮助用户在截止时间前发现可验证、可处理的问题。

## 2. 已确认的关键决策

| 决策 | 选择 |
| --- | --- |
| 第一版目标 | 投标文件提交前核查 |
| 核查深度 | 废标风险 + 评分得分点 |
| 可读取材料 | 招标文件、投标初稿、轻量企业资料库 |
| 发现问题后的能力 | 给出修改建议和待办清单，不直接改写最终 Word 文件 |
| Agent 方案 | 证据驱动的混合 Agent |
| 初始 Agent 数量 | 一个主 Agent + 确定性工具 |
| 初始模型路线 | 默认使用 OpenAI 模型，通过统一配置保留替换供应商的能力 |
| 产品形态 | 独立 Web 应用，前后端分离 |
| 用户范围 | MVP 为单用户，不建设复杂角色权限系统 |

## 3. 用户与现实问题

### 3.1 目标用户

- 中小型软件公司投标负责人；
- IT 服务商的商务、售前和项目经理；
- 为多个客户提供投标服务的咨询人员。

### 3.2 现实问题

招标要求通常分散在资格条件、投标人须知、技术需求、商务要求、评分标准和附件格式中。投标团队需要在有限时间内完成以下工作：

- 找齐所有实质性要求；
- 判断每项要求是否已经响应；
- 找到资质、案例、人员和证书等证明材料；
- 确认报价、签章、有效期、格式和截止时间；
- 尽可能覆盖评分项并提供充分证据。

漏掉一项实质性要求可能导致无效投标。司法部政府采购示范文本明确展示了符合性审查及不符合实质性要求时的无效投标处理方式。

## 4. 产品原则

### 4.1 证据先于结论

- 每条招标要求必须保存原文、页码和章节；
- 每个“已满足”必须引用当前投标初稿或企业资料的有效证据；
- 引用不存在、版本已过期或证据不足时，不得显示“已满足”。

### 4.2 不确定时诚实

以下情况进入“待确认”，不得强行判断：

- 招标条款存在多种解释；
- OCR 或文件解析不完整；
- 企业事实无法从材料证明；
- 招标文件前后矛盾；
- 企业资料有效期不明确。

### 4.3 人负责承诺，Agent 负责核查

- Agent 可以提出问题、查找证据和生成修改建议；
- 用户确认项目人员、驻场能力、交付承诺等企业事实；
- 系统不自动签章、不自动作出企业承诺、不自动提交投标。

### 4.4 Agent 与程序分工明确

Agent 负责理解要求、选择检索范围、评价证据充分性、决定继续查找还是追问用户。普通程序负责文件解析、版本控制、权限、状态计算、引用校验、持久化和恢复。

## 5. 完整用户流程

1. 用户创建投标项目，填写项目名称和截止时间；
2. 用户上传招标文件；
3. 系统解析 Word/PDF，保留页码、章节和文件版本；
4. Agent 分章节提取原子要求；
5. 程序去重、编号并验证引用，形成要求矩阵；
6. 用户上传投标初稿并选择本项目可用的企业资料；
7. Agent 对每条要求检索投标响应和企业证据；
8. 程序对引用与状态进行确定性校验；
9. 系统分别展示废标风险和评分改进项；
10. 用户查看问题详情，补充材料、指派处理或确认特殊情况；
11. 系统只重新核查受新材料或修改影响的要求；
12. 用户查看提交前状态并导出核查报告。

关闭浏览器不会终止后台任务。重新打开项目后可以继续查看进度和处理问题。

## 6. 要求矩阵

要求矩阵是产品的核心账本，不是一次性生成的报告。

### 6.1 每条要求保存的信息

- 要求编号；
- 招标要求原文；
- 来源文件版本、页码和章节；
- 要求类型；
- 所需证明材料类型；
- 投标初稿中的响应证据；
- 企业资料库中的证明证据；
- Agent 判断、理由和置信度；
- 风险等级；
- 用户确认；
- 负责人、处理动作和截止时间；
- 当前展示状态；
- 历次核查记录。

### 6.2 要求类型

- 资格要求；
- 实质性要求；
- 技术要求；
- 商务要求；
- 评分要求。

### 6.3 用户可见状态

| 状态 | 含义 |
| --- | --- |
| 高风险 | 可能导致无效投标或重大不合规 |
| 待补充 | 要求明确，但材料或响应不完整 |
| 可优化 | 基本合规，但可能损失评分 |
| 已满足 | 当前有效证据与要求匹配 |
| 待确认 | 必须由用户确认事实或解释 |

展示状态不直接采用模型输出，而是根据要求类型、证据状态、风险规则和用户确认计算。

## 7. 单条问题详情

问题详情将以下内容放在同一条处理路径中：

1. 招标要求原文及位置；
2. Agent 对要求结构的提取结果；
3. 投标初稿中的当前响应；
4. 企业资料库中的相关证据；
5. 判断结论与理由；
6. 可能影响；
7. 修改建议；
8. 用户可执行动作；
9. 历次补充、复核和状态变化。

用户可执行动作包括：上传补充材料、指派负责人、确认特殊情况、标记不适用、保留风险和补充后重新核查。

## 8. MVP 页面结构

### 8.1 核心页面

1. 项目首页：查看投标项目、截止时间、核查状态和风险数量；
2. 新建核查：依次上传招标文件、投标初稿并选择企业资料；
3. 核查总览：展示风险摘要、筛选器和要求矩阵；
4. 问题详情：展示完整证据链并处理单条问题。

### 8.2 支撑页面

1. 企业资料库：管理资质、案例、人员、证书和基础信息；
2. 核查报告：导出提交前结果、未解决事项和证据引用。

### 8.3 MVP 明确不做

- 复杂团队角色与权限；
- 自动编写完整投标方案；
- 直接提交到政府采购或企业采购平台；
- 自动签章；
- CRM、OA、网盘等企业系统集成；
- 用户自定义工作流设计器；
- 无人工确认的企业事实补全。

## 9. Agent 设计

### 9.1 采用一个主 Agent

MVP 不拆分多 Agent。一个主核查 Agent 通过结构化工具执行要求提取、证据检索、核查和追问。只有真实评测证明单 Agent 在职责边界上产生稳定问题时，才考虑拆分专门 Agent。

### 9.2 核心工具

- `get_document_outline`：读取文档结构与页码；
- `get_document_page`：读取指定页或章节；
- `search_tender_requirements`：检索招标要求；
- `search_proposal_evidence`：检索投标初稿响应；
- `search_company_evidence`：检索企业证明材料；
- `save_requirement`：保存经过结构校验的原子要求；
- `save_assessment`：保存判断、证据和风险信息；
- `request_user_confirmation`：创建需要用户确认的问题；
- `create_action_item`：生成可执行待办；
- `mark_review_scope`：标记增量复核的受影响范围。

工具参数使用严格结构。查询工具和修改状态的工具分开。具有状态变更效果的工具经过输入校验并记录审计事件。

### 9.3 有界核查循环

每次运行设置：

- 最大模型轮数；
- 最大工具调用次数；
- 最大自动重试次数；
- 单任务用量或费用上限；
- 单批要求数量；
- 需要人工确认的停止条件。

达到限制时保存当前结果，任务进入可恢复状态，不无限循环。

### 9.4 结果守门规则

- 招标要求没有有效原文引用时不得进入矩阵；
- “已满足”没有有效投标或企业证据时拒绝保存；
- 已过期或旧版本证据不能继续支持当前状态；
- 模型生成的企业事实不得作为证明材料；
- 高风险降级必须有新证据或用户确认；
- 待确认事项不能由 Agent 自行关闭。

## 10. 系统架构

```text
React Web 前端
      ↓
FastAPI 业务接口
      ↓
持久化任务记录
      ↓
后台任务执行器
      ↓
OpenAI Agents SDK + 自定义工具
      ↓
文档解析 / 检索 / 状态校验 / 数据库 / 文件存储
```

### 10.1 技术选择

- 前端：React、TypeScript、Vite；
- 后端：Python、FastAPI；
- Agent：OpenAI Agents SDK；
- 本地数据库：SQLite；
- 产品化迁移目标：PostgreSQL；
- MVP 后台任务：应用内持久化任务执行器；
- 文档输入：PDF、DOCX；
- 扫描件：识别为需 OCR，失败页明确暴露；
- 报告：先生成网页与可下载文件，最终格式在真实样本验证后确定。

MVP 不引入 n8n、Redis、Celery、复杂微服务或 Kubernetes。需要规模化、分布式运行或跨进程可靠队列时再升级基础设施。

## 11. 模型供应商策略

OpenAI Agents SDK 是 Agent 编排层，不要求业务永远绑定单一模型供应商。

MVP 默认使用 OpenAI 模型，以获得最完整的工具调用、结构化输出和 SDK 兼容性。模型通过统一配置层指定：

```text
MODEL_PROVIDER
EXTRACTION_MODEL
REVIEW_MODEL
```

业务代码与工具不写死模型名称。文档检索通过自有工具接口提供，不把核心证据链完全绑定到 OpenAI File Search。未来可通过 `ModelProvider` 或具体 `Model` 实现接入其他供应商。

非 OpenAI 模型的结构化输出、工具调用、多模态、使用量统计和追踪能力必须经过真实评测，不能因为接口兼容就宣称功能等价。

## 12. 数据模型

### 12.1 核心实体

- `BidProject`：一次投标项目；
- `Document`：招标文件、投标初稿或企业资料；
- `DocumentVersion`：不可覆盖的具体文件版本；
- `DocumentChunk`：带页码、章节和偏移信息的可检索文本；
- `Requirement`：招标文件中的原子要求；
- `Assessment`：某次运行对要求的判断；
- `EvidenceLink`：判断引用的具体文件位置；
- `ActionItem`：用户需要执行的处理事项；
- `Decision`：用户对关键事实的确认；
- `ReviewRun`：一次 Agent 核查或复核运行；
- `AuditEvent`：文件、状态、确认和任务变化记录。

### 12.2 版本规则

- 文件更新创建新版本，不覆盖旧版本；
- 招标文件更新后重新提取要求，并对比新增、删除和变化；
- 投标初稿更新后，根据变化段落确定增量复核范围；
- 企业证书过期或替换后，引用它的要求转为待复核；
- 报告绑定具体文件版本和核查运行；
- 所有历史判断保留，但不能冒充当前结果。

## 13. 后台任务与恢复

用户提交核查后，后端创建持久化任务。任务独立于浏览器连接继续运行，每完成一批要求就保存结果。

用户可见任务状态：

- 等待材料；
- 解析中；
- 提取要求中；
- 核查中；
- 等待确认；
- 可查看结果；
- 部分失败。

### 13.1 文件失败

扫描模糊或部分页解析失败时，系统列出失败页并要求重新上传。不得依据残缺文字生成“完整核查”结论。

### 13.2 模型或工具失败

超时、限流和工具失败采用有限重试。已完成结果立即持久化，达到重试上限后进入可恢复状态，从断点继续。

### 13.3 理解歧义

Agent 保存原文、候选解释和影响，将要求置为“待确认”。用户决定后再继续相关核查。

## 14. 安全与数据边界

- API Key 只保存在未提交的环境变量文件中；
- 文件类型、大小和访问路径接受后端校验；
- 用户只能访问自己的项目和文件；
- 模型只接收完成当前任务所需的文本片段；
- 日志不记录密钥和不必要的完整敏感文档；
- 所有状态变更记录操作来源；
- 外发模型数据、存储周期和删除策略在试点前向用户明确说明；
- 产品输出明确标注为辅助核查，不替代投标人承担真实性和提交责任。

## 15. 测试与评测

### 15.1 普通程序测试

- 文件解析与页码映射；
- 文件版本与哈希；
- 状态计算规则；
- 证据引用有效性；
- 增量复核范围；
- 任务断点与恢复；
- 权限与路径边界；
- 报告绑定的文件版本。

### 15.2 Agent 标准答案测试集

使用至少 8 份公开的软件或 IT 服务招标文件，人工标注：

- 至少 150 条资格和实质性要求；
- 至少 80 条评分要求；
- 对应页码和原文；
- 人为植入的材料缺失、响应矛盾和证据不足案例。

评测执行真实 Agent 路径，不只测试提示词或模拟工具输出。

## 16. MVP 验收标准

| 指标 | 目标 |
| --- | ---: |
| 资格与实质性要求召回率 | 不低于 95% |
| 评分项召回率 | 不低于 90% |
| 引用能够打开到有效文件位置 | 100% |
| 引用内容与判断相关 | 不低于 95% |
| 人为植入的高风险漏项 | 100% 发现 |
| 无证据却显示“已满足” | 0 次 |
| 编造企业资质、案例或承诺 | 0 次 |

### 16.1 功能完成条件

1. 用户可以独立走通完整核查流程；
2. 每条高风险判断能够追溯到当前有效证据；
3. 文件更新后能够正确保留历史并增量复核；
4. 浏览器关闭后任务继续运行；
5. 超时、限流、解析失败和中断后可以恢复；
6. 每次核查记录模型、工具、用量和错误；
7. 单任务可以配置调用次数和用量上限；
8. 至少完成一次约 200 页材料的全流程压力测试；
9. 至少完成一个真实公开投标项目的完整演示；
10. 测试、评测和实际运行结果被保存。

任何一次“无证据通过”或企业事实编造都属于阻止发布的问题。

## 17. 有意延后的决策

以下内容不是遗漏，而是等待真实验证后再决定：

- 精确模型组合：在标准答案测试集上比较质量、延迟和成本后选择；
- OCR 引擎：根据公开样本中的扫描件比例和中文识别质量选择；
- 最终报告格式：完成真实用户演示后决定优先 PDF 还是 DOCX；
- 云部署平台：本地 MVP 通过后，根据数据合规、预算和客户试点要求选择；
- 定价：根据节省时间、降低风险和客户试点反馈制定；
- 多 Agent：只有评测证明单 Agent 的职责边界不够清晰时才引入。
