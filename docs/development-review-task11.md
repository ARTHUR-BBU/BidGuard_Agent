# BidGuard Task 11 阶段复盘：从“有工具”到“能按规矩办事”

> 文档性质：开发复盘与能力边界说明，不是营销承诺。
>
> 复盘范围：Task 11「受控审核编排」。
>
> 当前基线：Task 11 已通过 PR #2 合并到 `main`，合并提交为 `7777942`。

## 1. 先说结论

Task 11 完成了 BidGuard 从“Agent 有一套受控证据工具”到“Agent 能按照规定的审核顺序使用这些工具”的关键跨越。

这一步已经证明：

- 一个 Requirement 可以被单独交给受限 Review Agent；
- Agent 被要求先阅读招标原文，再搜索投标和企业证据；
- 候选判断必须经过已有的引用、权限、证据和正式状态门禁；
- 缺证据、部分证据和歧义不会被包装成“已满足”；
- 审核中途失败时，已经完成的 Assessment 不会被一起丢掉；
- 运行进度、失败类型和模型调用可以留下可追溯记录。

但这一步还没有证明：

- 真实模型在真实招标材料上的业务准确率；
- 完整招标包是否已经覆盖；
- 企业投标响应是否已经完成正式合规核查；
- 系统是否可以自动提交投标、签章或承担最终承诺。

一句话概括：Task 11 造好了“审核流水线”，但还没有把它变成“无人值守的投标决策机器”。

## 2. Task 11 在整体开发地图中的位置

```text
Task 1   可运行工程骨架
   ↓
Task 2   统一领域状态和确定性规则
   ↓
Task 3   可追溯数据库和历史账本
   ↓
Task 4   项目与企业资料边界
   ↓
Task 5   安全、版本化文件资产
   ↓
Task 6   保留页码/章节的确定性解析
   ↓
Task 7   有项目范围的证据检索
   ↓
Task 8   OpenAI / EasyRouter 显式模型通道
   ↓
Task 8A  ReviewContext、预算、授权和调用台账
   ↓
Task 9   带引用的原子要求提取
   ↓
Task 10  受控证据工具和 unsupported-pass gate
   ↓
Task 11  受控审核编排  ← 本次
   ↓
Task 12  持久化进程内任务 worker
   ↓
Task 13  人工决定、ActionItem 和增量复核
```

这条顺序很重要。

Task 10 之前，系统是在准备档案、门牌、检索和门禁；Task 10 之后，Agent 已经有了“能读、能搜、能提交候选结果”的工具；Task 11 才真正回答了“这些工具应该按照什么顺序使用，以及失败后怎么办”。

如果跳过 Task 11，模型就像一个拿到很多工具但没有检查清单的人：它可能会调用工具，却没有可靠的流程、进度和恢复语义。

## 3. Task 11 解决了什么现实问题

在真实投标工作中，审核不是一次性问模型一句“我们能不能投”。它更像一张很长的检查表：

1. 先确认招标方到底要求什么；
2. 再看投标文件有没有响应；
3. 再看企业资质或业绩材料能不能支撑；
4. 找不到材料时，要标记缺失，而不是猜一个“应该有”；
5. 条款有歧义或事实需要负责人确认时，要停下来提问；
6. 审核中途出错时，已经查完的项目不能全部作废。

Task 11 把这张检查表变成了服务端控制的编排循环。

## 4. 本次实际交付了什么

### 4.1 一个只处理单个要求的 Review Agent

Agent 每次只收到一个明确的 Requirement，以及它在招标原文中的位置和引用。

它不能自己选择任意项目，也不能通过输入参数扩大文档范围。这样做牺牲了一些“看起来很自由”的感觉，却换来了可定位、可审计和可恢复。

### 4.2 固定的证据阅读顺序

Review Agent 的规则明确要求：

```text
先读要求原文
  → 搜索投标证据
  → 搜索已授权企业证据
  → 打开最相关的原文页面
  → 形成候选判断
  → 保存 Assessment
  → 必要时请求人工确认
```

这不是为了让提示词看起来漂亮，而是为了避免模型跳过原文、只凭关键词命中就下结论。

### 4.3 复用服务端正式状态规则

模型可以提出 `AssessmentCandidate`，但不能直接决定正式展示状态。

正式状态仍由服务端计算：

| 情况 | 服务端状态 |
|---|---|
| 强制要求缺少证据 | `high_risk` |
| 评分项只有部分证据且有优化空间 | `optimize` |
| 证据充分并通过引用门禁 | `satisfied` |
| 条款或企业事实需要人确认 | `needs_confirmation` |

特别是 `MATCHED` 没有真实引用时，Task 10 的 `unsupported-pass` 门禁仍然会阻断它。Task 11 没有绕过这个门。

### 4.4 失败后保留进度

Task 11 处理的是现实中一定会发生的情况：模型超时、工具次数用完、供应商异常或输出结构不符合要求。

当前行为是：

- 已经保存的 Assessment 提交保留；
- ReviewRun 标记为 `partial_failure`；
- 记录失败的 Requirement；
- 保存可恢复的 Requirement 游标；
- 写入进度和失败审计事件；
- 不把“部分完成”伪装成“全部完成”。

这就像填一张 100 项的验收表，填到第 37 项时电脑断电，系统至少要保住前 36 项，并告诉我们下次从第 37 项继续，而不是重新声称“全部完成”。

### 4.5 人工确认不是摆设

当候选判断依赖未核实企业事实或条款存在歧义时，系统会创建可审计的人工确认请求，并把状态保留为 `needs_confirmation`。

它不会：

- 替负责人回答事实问题；
- 把确认请求当作证据；
- 自动把正式状态改成“满足”；
- 删除原来的不确定性。

## 5. 本次测试分别证明了什么

Task 11 专项测试共有 5 项：

| 测试场景 | 它证明的边界 |
|---|---|
| 匹配证据 | 有效引用可以保存为 `satisfied` |
| 强制项缺证据 | 缺失材料不会被误报为通过，而是 `high_risk` |
| 评分项部分证据 | 部分响应可以进入 `optimize`，而不是粗暴地判定满足 |
| 歧义要求 | 系统会留下人工确认请求并进入 `needs_confirmation` |
| 中途超时 | 已完成结果保留，运行进入 `partial_failure` 并可恢复 |

最终验证证据：

- Task 11 专项测试：`5 passed`；
- 后端全量测试：`273 passed`；
- Ruff：通过；
- Mypy：通过；
- 真实业务模型：本阶段未调用，使用注入式 Runner 验证编排和失败语义。

## 6. Task 11 给 Agent 增加了什么权力，又没有增加什么权力

### 新增的有限能力

- 按顺序调用受控证据工具；
- 对单个 Requirement 形成结构化候选 Assessment；
- 请求人工确认；
- 创建受控的开放 ActionItem；
- 在服务端预算内继续处理下一项要求。

### 明确没有新增的权力

- 不能改变项目范围；
- 不能读取未授权企业材料；
- 不能把搜索分数当成事实；
- 不能绕过引用真实性验证；
- 不能直接写正式状态；
- 不能代替人工做最终投标承诺；
- 不能自动提交、签章、审批、付款或写入外部系统；
- 不能在失败后把部分结果包装成完整审核。

这就是 BidGuard 的核心分工：

```text
原文定义要求
  → 当前证据支撑事实
  → LLM 负责理解与质疑
  → 程序负责验证与制衡
  → 人工负责承诺与最终提交
```

## 7. 为什么 Task 11 仍然不能叫“完整 Agent 审标”

因为“能运行一条受控循环”和“在真实招标包上可靠工作”是两件不同的事。

当前还缺少：

- 真实招标文件集上的模型质量评测；
- OCR、复杂表格、附件和非正文内容的完整覆盖；
- 后台持久化任务 worker；
- 人工决定 API；
- 增量复核和版本变化后的影响分析；
- 完整前端审核流程；
- 报告导出和对外协作流程。

所以当前准确的产品表述是：

> BidGuard 已具备一个程序化受控的、证据可追溯的审核编排底座。

而不是：

> BidGuard 已经可以自动完成投标审核并保证投标结果。

## 8. 对收费垂类产品目标的意义

Task 11 让产品第一次具备了可以演示“审核过程”的形态，而不只是展示底层技术：

- 客户可以看到某条要求从原文到证据再到候选判断的过程；
- 客户可以看到缺证据时系统如何停下，而不是胡乱给答案；
- 客户可以看到中途失败后结果仍然保留；
- 企业可以把人工确认和补材料变成可追踪事项。

这正是垂类产品可以收费的地方：不是卖一个泛泛的聊天框，而是卖一条有证据、有边界、有责任分工的投标质量流程。

但真正收费前仍需完成真实材料评测、用户流程验证、稳定性验证和数据安全审查。Task 11 证明了“流程骨架可演示”，还没有证明“客户愿意为准确率和结果负责”。

## 9. 下一步为什么是 Task 12

Task 11 现在仍然是一次调用一次编排。它能正确处理失败，但还没有一个可以可靠接收、排队、恢复和查看状态的后台任务系统。

Task 12 要解决的是：

- 审核任务如何进入队列；
- 服务重启后如何恢复；
- 一个任务如何记录状态和进度；
- 如何避免同一任务被重复执行；
- 如何把长时间审核从前端请求中分离出来。

类比来说，Task 11 是把审核员训练好并给他检查清单；Task 12 是给审核部门建立值班台、排班表和交接制度。

## 10. 最终复盘

Task 11 的真正价值不是“多写了两个 Python 文件”，而是把 Agent 从“会调用工具”推进到“在制度内完成一段可恢复工作”。

它位于产品从工程地基走向真实业务流程的转折点：

- 前面 1—10 解决了材料、范围、证据、模型和工具的可信基础；
- Task 11 解决了这些能力如何连成一条受控业务链；
- 后面的 12—13 才会解决长任务运行、人工决定和增量复核；
- 再之后，才有资格讨论完整前端、报告、真实客户试用和收费交付。

因此，Task 11 已经完成，但它完成的是“受控编排底座”，不是“自动投标产品终点”。
