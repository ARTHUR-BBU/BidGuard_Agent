# BidGuard Task 12 阶段复盘：给审核员建立“后台工位”和交接制度

> 文档性质：开发记录与能力边界说明，不是营销承诺。
>
> 复盘范围：Task 12「持久化进程内任务 Worker」。
>
> 验收基线：277 个后端测试通过，Ruff 与 Mypy 通过；真实业务模型质量仍未验收。

## 1. 先给结论

Task 11 已经让 BidGuard 知道“审核时应该按什么顺序做事”，Task 12 又解决了“用户离开页面以后，谁继续把这件事做完”。

现在，用户提交审核后，系统会先在数据库登记一个 `ReviewJob`，再由后台 Worker 领取任务。任务会留下 `queued → running → parsing → extracting → reviewing → completed/awaiting_confirmation/failed` 等真实阶段。进程意外停止时，遗留的 `running` 任务会在下次启动时回到队列，并增加尝试次数。

这一步让 BidGuard 从“当前请求里调用一次 Agent”向“可以记住工作、恢复工作、查看工作状态的 Agent 应用”迈进了一大步。但它仍然不是自动投标系统，也没有替用户作最终承诺。

## 2. 为什么必须有 Task 12

Task 11 像一个坐在窗口前的专业审核员：你站在旁边，他可以逐条检查要求、寻找证据、保存判断。

现实问题是，招标文件可能很长，模型可能超时，浏览器可能关闭，服务可能重启。如果审核只存在于当前 HTTP 请求里，做到一半就会出现“前面已经做完的工作没人知道，后面也没人接着做”。

所以 Task 12 建立的是后台工位：数据库是交接本，Worker 是值班审核员，阶段字段是工作牌。它不让模型更聪明，而是让已有的受控审核流程能够稳定地持续运行。

## 3. 它在整个系统中的位置

```text
Task 1—9：档案、版本、解析、检索、要求提取和引用门禁
        ↓
Task 10：受控证据工具箱
        ↓
Task 11：按要求运行 Review Agent 的审核流水线
        ↓
Task 12：持久化 ReviewJob + 后台 Worker + 状态 API  ← 本次
        ↓
Task 13：人工决定、行动项和增量复核
        ↓
Task 14+：前端工作台和报告体验
```

Task 12 连接了“Agent 会审核”和“用户能把审核交给系统持续执行”这两层。没有它，Task 11 的流程只能靠用户一直守在请求旁边；有了它，前端以后才能可靠地展示任务状态和审核结果。

## 4. 本次真正落地的能力

### 4.1 可持久化的任务事实

`ReviewJob` 记录项目、ReviewRun、招标版本、当前文件版本指纹、版本集合、阶段、状态、尝试次数、领取时间、结束时间和错误信息。任务状态先写数据库，不能只存在内存里。

### 4.2 原子领取和中断恢复

Worker 领取任务时使用“先找到、再带状态条件更新”的原子语义，多个领取者不会把同一个任务当成两个任务执行。启动时会把遗留的 `running` 任务重新放回 `queued`，并保留“上次进程中断”的原因；下一次领取时 `attempt_count` 增加。

### 4.3 可查看的真实阶段

系统只记录已经发生的阶段，不计算没有证据来源的“完成 73%”。阶段包括解析、要求提取、逐项审核、等待人工确认、完成和失败。这样前端显示的是事实，不是看起来精确的猜测。

### 4.4 审核 API

新增接口支持启动审核、查询最新任务、查看要求列表和查看单条要求详情。启动相同项目和相同活动文件版本时，已有的活动任务会被复用，避免重复消耗模型额度。

### 4.5 与既有 Agent 门禁复用

Worker 不绕过 Task 9 的引用门禁、Task 10 的受控工具和 Task 11 的 `ReviewContext`。它负责安排和恢复工作，不能把模型输出直接变成正式合规结论。

## 5. 这一步解决了什么现实问题

```text
用户提交审核
    ↓
数据库登记 ReviewJob
    ↓
Worker 领取并记录 attempt_count
    ↓
解析 → 提取（必要时）→ 逐项审核
    ↓
保存 Assessment、调用台账和审计进度
    ↓
完成 / 等待人工确认 / 失败并保留原因
```

如果第 38 条要求调用超时：

```text
前 37 条已提交
第 38 条失败
任务留下 resumable_requirement_id 和错误记录
服务重启后任务回队列
后续可以从可恢复位置继续
```

这就是“持久化”的实际含义：不是让系统永不失败，而是失败时不把已经完成的工作抹掉。

## 6. 验收证据

- Task 12 专项测试：4 项通过，覆盖入队、原子领取、尝试次数、中断回队、完成持久化、Worker 结果保存和重复启动去重；
- 后端全量测试：277 项通过；
- Ruff：通过；
- Mypy：42 个源文件无问题；
- 旧 SQLite 数据库：新增任务字段通过安全增量迁移路径；
- FastAPI lifespan：启动时恢复中断任务，关闭时发送停止信号，不删除任务。

## 7. 本次没有完成、也不能冒充完成的内容

- 仍是单用户、本地、单进程 Worker，不是 Redis/Celery 分布式队列；
- 没有租约心跳、并发 Worker、优先级队列或多租户隔离；
- 没有人工决定 API、增量复核、完整前端任务页和报告导出；
- 没有证明真实招标文件上的模型准确率、召回率或稳定性；
- `completed` 只表示程序完成了当前审核流程，不表示投标一定合规，更不表示可以自动提交。

## 8. 下一步因果链

Task 12 暴露的下一个现实问题是：Worker 可以停在 `awaiting_confirmation`，但用户还没有正式的确认、否决和“不适用”入口；如果没有这个入口，系统只能发现不确定性，却不能把人的承诺记录回流程。

因此下一步是 Task 13：人工决定、行动项和增量复核。它要把“发现问题”接成“人确认后重新核查”，同时确保新文件版本只让受影响的要求重新进入审核。
