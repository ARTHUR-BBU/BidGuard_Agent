## 第六章 · 要求先钉在原文上，再进入后续审核（09-21，Task 9）

### 这次做了什么（大白话）

- **做了一个“拆单员”**：把招标摘录里的复合要求拆成后续可以逐条核对的原子要求，但不替人判断企业是否合规。
- **给每条要求装上“门牌号”**：模型必须给出当前招标版本、页码或章节和最小原文引用；引用不在授权片段里，就不入库。
- **把两种指纹分开**：一枚指纹表示“要求内容是什么”，另一枚表示“它引用了哪个版本、哪一页/章节”，避免同一句话在不同位置被错误合并。
- **保留历史**：换了新的招标版本，旧要求只变成 inactive，不删除，方便追溯“当时依据了哪一版文件”。
- **把模型调用记账**：真正执行 Runner 时必须写入安全台账；正文摘录还必须与数据库授权 chunk 完全对应，防止把外部提示注入混进模型输入。

### 先说难堪的

这一步仍然没有把真实招标文件文本交给模型。现在通过的是“程序边界 + mock 模型响应”的合约测试，不是模型业务质量测试，也不是完整招标包审核。

- `Constitution impact: Yes` 已单独记录在 `docs/governance/task-9-constitution-impact.md`。

## 第七章 · 给 Agent 一套有门禁的证据工具箱（Task 10）

### 这次做了什么（大白话）

- **允许它看小块证据**：Agent 可以读取授权版本的指定页，也可以搜索当前项目中已经授权的投标响应和企业资料，但拿不到整份文档。
- **允许它提交候选意见**：Agent 可以提交 Assessment 候选、请求人工确认、创建行动项；这些都是“待程序和人工继续处理的草稿”，不是最终裁定。
- **给“已满足”装上刹车**：如果候选 Assessment 写成 `MATCHED` 却没有 Evidence，程序直接拒绝；旧版本、跨项目、引用不存在的 quote 也不能保存。
- **正式状态由程序计算**：模型不能自己写 `satisfied`。服务端根据 Requirement、EvidenceState、Severity 和人工确认规则计算展示状态。

### 先说难堪的

Task 10 仍然没有把完整审核流程交给模型。当前只是把工具箱造好并装上门锁；Review Agent 编排、后台任务、人工决定和增量复核还没有实现。

### 给您的交代

- `Constitution impact: Yes` 已单独记录在 `docs/governance/task-10-constitution-impact.md`。

## 第三章 · 搜索可以帮忙找证据，但不能替证据盖章（09-19，PR 号待补 · Task 7 模型无关检索收官）

### 这次做了什么（大白话）

- **先把“找得到”做扎实**：系统按文字重合度寻找候选片段，像档案员先把相关页码放到桌上；它不会因为搜到了几个词，就宣布企业已经符合要求。
- **检索范围有围墙**：每次搜索必须带项目编号，服务端逐个核对版本是否属于这个项目。跨项目、过期或非法版本会整次拒绝，不会返回一部分“看似有用”的结果。
- **覆盖不完整就亮黄灯**：解析状态不是唯一依据。缺页、OCR、异常 Coverage、部分解析都会保留候选，但明确标记不完整；后续 Agent 不能把它当作全量证据。

### 先说难堪的

第一版检索通过了自动测试，却被独立验收连续拦下：先是发现版本 ID 只靠调用方自觉，可能跨项目取证；接着发现异常 Coverage JSON 可能被误判为完整。我们连续补了权限绑定和 fail-closed 校验，直到独立复审达到 Critical 0、Important 0、Minor 0 才收口。

## 第八章 · 把证据工具箱接成受控审核循环（09-22，PR #2 · Task 11）

### 这一步为什么重要（大白话）

Task 10 已经造好了“带门锁的证据工具箱”，但工具箱自己不会排队工作。Task 11 把它接成一条审核流水线：每次只看一个要求，先看招标原文，再找投标和企业证据，最后保存候选判断。

它像给档案室配了一名受监督的审核员。审核员可以按清单逐项处理，但不能换项目、偷看未授权材料，也不能自己盖“合规”印章。

### 这次做了什么

- 新增单要求、结构化输出的受限 Review Agent；
- 新增按要求逐项运行的服务编排，批次上限为 10；
- 复用已有证据工具、引用校验和服务端状态规则；
- 歧义结果自动留下人工确认请求；
- 中途超时或工具/轮次受限时，提交已完成 Assessment，并记录可恢复要求游标；
- 记录进度事件、失败类型和安全模型调用台账；
- 同步中英文 README 与 Task 11 宪法影响记录。

## 第九章 · 给审核员建立后台工位和交接制度（09-22，Task 12）

### 这次为什么做

Task 11 已经让 Agent 按规矩逐条审核，但它仍像“坐在窗口前等人盯着干活的审核员”：请求结束、浏览器关闭或服务重启后，任务缺少可靠的接班机制。Task 12 把审核登记成数据库里的 `ReviewJob`，再交给后台 Worker 继续处理。

### 这次做了什么（大白话）

- **建立任务交接本**：记录项目、文件版本指纹、审核运行、阶段、尝试次数、错误和完成时间；
- **建立后台值班位**：Worker 原子领取任务，按“解析 → 必要时提取 → 逐项审核”执行；
- **建立中断恢复**：服务重启时，把遗留的 `running` 任务重新排队，保留中断原因；
- **建立状态查询入口**：可以启动审核、查询最新任务、查看要求列表和单条要求详情；
- **复用已有门禁**：Worker 只负责安排和恢复，不能越过 ReviewContext、证据工具、引用真实性和模型调用台账。

### 先说难堪的

全量回归第一次运行时发现，测试替换了临时数据库，但 Worker 仍握着模块启动时的旧连接，导致它找不到新字段。这不是“再加一个 if”能解决的问题，而是应用生命周期和数据库边界没有对齐。现在 Worker 在启动时根据当前 engine 创建 session factory，测试与嵌入式部署都能使用正确的数据库。

另外，后台默认审核路径暴露出 Task 11 的一个隐蔽缺口：底层编排在未传入指定要求列表时没有真正查询全部有效要求。已修正并加入重复启动回归测试，避免“接口能排队、Worker 一启动就失败”。

### 给您的交代

- Task 12 专项测试 **4 项通过**；
- 后端全量测试 **277 项通过**；
- Ruff、Mypy 通过；
- 新增 Task 12 规格、阶段复盘和 Constitution Impact 文档；
- 当前仍不能宣传为自动投标、自动提交、自动签章或中标保证系统。

### 当前边界与下一步

现在系统具备“可排队、可恢复、可查状态”的后台审核骨架，但用户还不能正式确认、否决或标记“不适用”，也没有增量复核和完整前端任务页。下一步是 Task 13：把 `awaiting_confirmation` 接成人的正式决定，并让新材料只触发受影响范围的复核。

## 第十章 · 把“待确认”接成人的决定，再按变化范围复核（09-22，Task 13）

### 这次为什么做

Task 12 可以让审核停在 `awaiting_confirmation`，但没有正式的人工确认、否决和“不适用”入口；材料更新后，也没有办法判断哪些旧结论已经过期。Task 13 把人的责任和版本变化重新接回审核证据链。

### 这次做了什么（大白话）

- **建立人工决定台**：`confirm`、`deny`、`not_applicable` 都要求责任人和解释，并留下审计事件；
- **把 Agent 的待确认事项记下来**：`pending` Decision 不再只是一条聊天式事件，不能被静默删除；
- **行动项有完成回执**：记录谁完成了什么、何时完成，但不把按钮点击冒充成合规证据；
- **建立版本影响计算**：proposal、企业资料和 tender 变化时，只让受影响 Assessment 失效；
- **保留历史、重新排队**：旧 Requirement、Assessment 和证据不删除，受影响 Requirement ID 先写入 ReviewRun，再交给 Worker。

### 先说难堪的

Task 13 不是简单增加三个接口。真正的难点是避免“人工确认”变成洗状态的按钮，也避免新版本上传后旧结论继续冒充当前结论。因此决定记录、EvidenceLink、Assessment.current、Requirement.active 和 ReviewRun.affected_requirement_ids 必须同时工作。

## 第二章 · 文件会说话，也会承认自己没看见（09-18，PR 号待补 · Task 6 文档解析收官）

### 先说难堪的

第一版虽然测试全绿，独立验收仍两次拦门：先发现 PDF 附件、Word 页眉页脚、异常中断等内容可能被静默漏掉；修完后，又发现两个同名章节会被合并。原实现代理中途还遇到使用额度中断。代码没有丢失，但这说明“实现者自证通过”不能代替独立验收。现在这条规矩已落实为：实现、攻击式复审、修复、再次复审，缺一不可。

### 这次做了什么（大白话）

- **每段文字都带地址**：PDF 记真实页码，Word 记标题路径和物理章节序号。两个都叫“资格要求”的章节，也像同名住户拥有不同门牌，不会再混成一处。
- **看不见就主动举手**：扫描页、附件、图片、复杂表格、页眉页脚等当前不能完整提取的内容，会进入结构化“覆盖范围”记录，并把结果标成不完整；系统不能把“我没看到”说成“文件里没有”。
- **解析任务可以安全接班**：任务意外中断后，超过 15 分钟的旧任务可由新尝试接管；较旧结果不能覆盖较新结果，失败重试也不会毁掉上一次成功快照。
- **旧账本没有被拿来试刀**：数据库升级使用增量方式，测试在隔离环境完成，没有删除或重建真实本地数据库。

## 第四章 · 给模型接电，但先不把标书插上去（09-20，PR 号待补 · Task 8 模型边界收官）

### 这次做了什么（大白话）

- **把模型开关集中管理**：像给整栋楼只留一个总闸，提取模型和复核模型从统一配置进入，Agent 代码不各自私藏供应商和模型名。
- **模型没配好就停在门口**：缺少模型名、供应商不支持或配置用途写错，程序给出稳定错误码；健康检查和文件解析仍然可以工作。

## 第五章 · 模型先领门禁卡，才能看业务材料（09-21，PR 号待补 · Task 8A 治理门禁）

### 这次做了什么（大白话）

- **给模型准备一张“只在本项目有效”的门禁卡**：`ReviewContext` 由服务端写入项目、招标版本、企业资料版本、可见片段和预算；模型不能靠自己传一个新的项目编号或版本编号来扩大范围。
- **把“看了哪些、没看哪些”记成正式 Coverage**：完整、部分失败、待人工确认三种状态不能混写。没有检查的范围必须写出来，像盘点仓库时明确哪些货架还没开箱。
- **建立调用账本**：每次模型尝试保存供应商、模型、Prompt 版本与哈希、输入对象编号、覆盖范围、结果、失败码、耗时、重试、用量和停止原因；默认不保存整段 Prompt、整份文件或密钥。
- **企业资料必须被项目明确选入**：不是“系统里存在”就能给模型看；选入关系会记录操作者和时间，并在生成上下文时再次验明确实属于企业资料。
- **招标补遗和澄清不能靠模型猜先后**：招标包记录纳入/排除、效力顺序和冲突；冲突未解决时直接停在人工确认。
- **预算先验算，再允许调用**：轮次、工具次数、重试、超时、token、费用和批量都有服务端上限，耗尽后停止，不会自动放宽。
