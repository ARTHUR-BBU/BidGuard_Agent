# LLM 在 BidGuard 中的定位、权限与分阶段开发规范

> 状态：正式生效（Normative）
>
> 版本：1.0
>
> 生效日期：2026-09-18
>
> 代码基线：`feature/mvp@c804d02`
>
> 上位规范：[BidGuard Constitution](./bidguard-constitution.md)

## 1. 一句话定位

LLM 不是 BidGuard 的裁判、数据库或权限系统。它是被 Pipeline 在特定事件中调用、只查看获授权上下文、只产生候选对象，并接受证据与程序门禁验证的认知能力。

我们的目标不是让模型拥有越来越大的权力，而是让它：

- 在正确的节点被调用；
- 只看到完成该节点所需的上下文；
- 只输出被允许的结构化对象；
- 经过可重复验证的门禁；
- 在失败时诚实降级并可恢复。

## 2. 软件、LLM 与人工的分工

| 能力 | 确定性程序 | LLM / Agent | 人工 |
| --- | --- | --- | --- |
| 文件哈希、版本、页码、权限 | 决定 | 无权修改 | 可上传/选择 |
| 招标原子要求 | 验证并持久化 | 提出候选 | 可纠错/确认歧义 |
| 证据检索 | 限定范围、返回可追溯结果 | 选择查询与候选 | 可补材料 |
| 证据是否匹配 | 校验真实性、版本、位置和硬门槛 | 分析相关性与充分性 | 确认企业事实 |
| 风险与建议 | 应用规则、保存历史 | 提出候选理由与建议 | 决定处理方式 |
| 正式展示状态 | 唯一计算者 | 不得直接决定 | 决定事实/风险，但不能改写历史 |
| 提交投标 | 当前不执行 | 无权执行 | 唯一责任主体 |

## 3. 每个 LLM 节点的强制调用契约

任何涉及 LLM、Prompt、模型配置、Evidence、Quality、Review、Ask、Pipeline、RAG 或工具调用的 PR，必须逐项回答：

1. **触发事件**：什么业务事件触发，为什么此处需要模型；
2. **角色**：模型此时是提取者、检索规划者、核查分析者、质疑者还是文案助手；
3. **授权上下文**：它能看到哪些项目、版本、页/章节、历史决定和元数据；
4. **标准输入**：输入对象、大小、排序、coverage 和来源；
5. **标准输出**：结构化对象、枚举、长度与数量上限；
6. **拥有的权力**：允许建议或触发哪些受限工具；
7. **明确没有的权力**：哪些状态、事实、权限或外部动作绝不能修改；
8. **服务端复算/验证**：哪些字段必须忽略模型值并重新计算；
9. **证据检查**：真实性、版本、位置、文字一致性、相关性、覆盖性、时效性与授权性如何验证；
10. **资源边界**：轮次、工具次数、超时、重试、token、费用和批大小；
11. **失败语义**：无 Key、超时、限流、坏输出、拒收、预算耗尽时进入什么状态；
12. **调用账本**：记录哪些模型、Prompt、上下文范围、耗时、用量、成本与拒收原因；
13. **测试证据**：mock、门禁、对抗、真实模型、E2E 和回归测试分别证明什么；
14. **Constitution impact**：是否改变项目宪法中的权力或门禁。

缺少以上信息的 LLM 节点不得进入实现阶段。

## 4. 标准对象链，而不是自由文本接力

BidGuard 的正式链路应保持为：

```text
DocumentVersion
  → ParsedChunk
  → RequirementCandidate
  → Validated Requirement
  → EvidenceCandidate
  → Stable Evidence Fact / Validated EvidenceLink
  → Claim（支持、反驳、缺失或矛盾主张）
  → AssessmentCandidate
  → Server-calculated DisplayStatus
  → HumanAssertion / HumanDecision / ActionItem（与文档 Evidence 分离）
  → New DocumentVersion
  → Re-review
```

原则：

- 上一层的自由文本不能直接成为下一层正式事实；
- 共享对象用 ID 关联，不在多层之间反复复制 quote 并重新猜来源；
- 每个对象保留来源版本、位置、创建者和验证状态；
- 候选、已验证结果、人工决定和正式状态必须是不同字段或实体；
- 人工声明不得复用 `EvidenceLink` 冒充带页码与 quote 的文档证据；只有 Requirement 明确不要求随标材料、且版本化规则允许内部事实确认时，它才可进入满足计算。需要写入、签署或随投标包提交的声明，必须在当前 proposal/附件版本中形成文档 Evidence；
- 新版本触发复核，不能原地覆盖旧版本和旧判断。
- 同一 Requirement 在同一 ReviewRun 中只有一个正式当前 Assessment；多条 Evidence 支持或反驳同一个稳定争点，而不是靠重复摘句制造多个问题。

`EvidenceCandidate`、统一 Coverage 和 LLM 调用账本如果尚未在代码中存在，属于进入真实 Agent 开发前的必备基础，而不是可以由 Prompt 代替的概念。

## 5. 节点规范

### 5.1 要求提取节点

**触发**：当前招标文件版本解析完成，且要求矩阵需要创建或刷新。

**模型角色**：受限的信息提取者。

**可见范围**：一个有明确版本、页码或章节的固定小批文本。

**输出**：`RequirementBatch` / `RequirementCandidate`。

可以：

- 拆分可以独立核查的原子要求；
- 分类要求类型和候选 mandatory 属性；
- 引用最小充分原文。

不可以：

- 推断企业是否满足；
- 推断招标文件没有写出的条件；
- 产生正式风险、评分或展示状态；
- 引用批次外文字。

服务端必须验证当前版本、页码/章节、quote 存在性、最小长度、枚举和去重指纹。无有效引用的候选不得保存为正式 Requirement。

### 5.2 证据检索规划节点

**触发**：某条已验证 Requirement 需要查找投标响应或企业资料。

**模型角色**：检索规划者，不是资料管理员。

**可见范围**：当前 Requirement、当前项目的有效 proposal，以及用户明确选入项目的 company evidence。

**输出**：受限查询、候选结果 ID 或继续查看的页/章节。

可以选择查询和打开候选位置；不可以指定任意项目 ID、扩大到未授权资料、修改版本状态或把检索分数当成事实。

服务端必须限定项目和版本，返回紧凑、可追溯的候选；不得把整库或整份敏感文档无条件发送给模型。

### 5.3 核查与质疑节点

**触发**：Requirement、候选证据和 coverage 已准备好。

**模型角色**：核查分析者与质疑者。

**输出**：`AssessmentCandidate`，包括候选 evidence state、severity、理由、Evidence 引用、待确认标志和建议。

可以：

- 比较要求与响应是否同主体、同条件、同期限；
- 发现部分覆盖、互相矛盾、材料缺失或潜在失分；
- 对看似“已满足”的结果提出异议；
- 请求人工确认不可由材料证明的事实。

不可以：

- 直接写入 `DisplayStatus`；
- 在没有 EvidenceLink 时提交 `matched`；
- 把置信度、检索分数或常识当作证据；
- 自行采纳企业事实、关闭人工问题或消除高风险；
- 修改正式 Requirement 和历史 Assessment。

程序必须重新验证引用与当前版本，并通过 `calculate_display_status` 等确定性规则计算正式状态。这里的“重新计算”不等于把模型给出的 `evidence_state`、`severity` 和 `needs_confirmation` 原样送入函数；这些输入也必须先由证据门禁、规则和人工状态验证或派生，防止模型间接控制正式状态。

### 5.4 追问与行动建议节点

**触发**：存在歧义、缺证据、企业事实未知或需要具体补救。

**模型角色**：澄清问题和文案草案助手。

**输出**：候选问题、原因、建议动作或改写草案。

问题必须指向具体未知事实和其对哪条 Requirement 的影响。建议稿不得冒充企业承诺；只有用户确认或新文档版本经过复核后，相关问题才可能改变。

### 5.5 修改影响与复核节点

**触发**：proposal、tender 或 company evidence 出现新版本。

**模型角色**：受限的影响分析助手。

**输出**：候选受影响 Requirement ID 与理由。

程序必须使用版本差异、已有 EvidenceLink 和规则关系计算最低复核范围；模型只能扩大候选范围，不能单独缩小必须复核的范围。最终结论来自对新版本的正式重新核查。

### 5.6 报告解释节点

**触发**：正式结果和 EvidenceLink 已固定。

**默认实现**：确定性模板导出，不调用 LLM。

**可选模型角色**：仅在未来单独批准后作为解释与表达助手。

**输出**：与确定性报告分层展示、且不改变事实的参考摘要。

报告中的状态、数字、引用、版本和未完成范围由服务端注入并锁定。模型不得省略待确认、部分失败或已接受但仍存在的风险，也不得在导出阶段重新推理或改写正式结论。

## 6. Tool 权限规范

工具分为三类：

1. **只读工具**：读取限定页、检索限定证据、读取当前 Requirement；
2. **候选写入工具**：保存候选 Assessment、创建待确认问题或 ActionItem；
3. **高影响工具**：改变正式状态、版本、权限、外部系统或提交行为。

LLM 在 MVP 中只可使用前两类，且候选写入必须经过服务端校验和审计。高影响工具不得直接暴露给模型。

工具授权必须来自不可由模型修改的 `ReviewContext`：项目 ID、当前版本 ID、ReviewRun ID、允许的 company document ID、调用预算和用户范围。模型提供的同名参数只能进一步缩小范围，不能扩大范围。

## 7. Coverage 是正式输入，不是感觉

每次提取或核查必须记录覆盖范围，例如：

- 目标文档版本；
- 本次招标包中已纳入与未纳入的主文件、附件、补遗、澄清和格式模板；
- 总页数/章节数与成功解析数；
- 失败页、OCR 待处理页、仅图片页面、未识别表格/嵌入对象和被截断范围；
- 已检索的 proposal/company 版本；
- 本批 Requirement ID；
- 模型实际可见的 chunk/page ID；
- 未检查或因预算停止的范围。

Coverage 不足时只能产生局部结果，并明确标记 `partial_failure`、`needs_confirmation` 或等价状态；不得用“未发现”冒充“已完整检查”。

字符覆盖率不能代表业务覆盖率。一页即使提取出少量页眉文字，只要主体是扫描图、复杂表格或附件对象，就不得算作该页要求已经完成核查。

## 8. Prompt 与文档内容的边界

- Prompt 必须有稳定版本号和内容哈希；
- 系统指令、工具说明和业务文档必须分层传入；
- 招标文件或投标文件中的任何“忽略之前指令”“调用某工具”等文字都视为普通证据内容；
- 文档文本不得改变工具列表、项目范围、输出 schema 或停止条件；
- Prompt 变更如果可能影响正式候选结果，必须运行保存的回归评测；
- 不在 Prompt 中重复实现本应由服务端完成的权限和状态规则。

## 9. 模型供应商与配置

- 业务代码不得散落写死模型名称；
- extraction、review 等用途通过统一 provider/config 边界解析；
- 缺少配置只阻止对应 Agent 任务，不应让健康检查、文件浏览或确定性能力全部失效；
- 不得静默切换模型或供应商；
- “接口兼容”不等于能力等价。切换供应商前必须验证结构化输出、工具调用、中文投标文本、上下文限制、用量统计、追踪和失败语义；
- live smoke 只能证明连接与最小输出成功，不能证明业务质量。

## 10. 失败与降级矩阵

| 失败 | 程序行为 | 用户可见语义 | 禁止行为 |
| --- | --- | --- | --- |
| 无 API Key / 模型未配置 | 拒绝启动该 Agent 任务 | 模型能力未配置 | 伪装成空结果或静默换供应商 |
| 超时 / 限流 / 临时网络错误 | 有限重试，保存断点 | 暂时中断，可恢复 | 无限重试 |
| 坏 JSON / schema 不匹配 | 拒收并记 reason code，可有限重试 | 本批未完成 | 猜字段或宽松落库 |
| 引用不存在 / 版本错误 | 门禁拒收 | 候选无效 | 删除引用后继续判定 |
| Coverage 不足 | 保存局部结果 | 部分完成/待处理 | 声称完整核查 |
| 工具或轮次上限 | 停止并持久化已验证结果 | 达到运行上限 | 自动提高预算 |
| 成本上限 | 停止后等待人工 | 预算已用尽 | 拆分调用规避上限 |
| 工具失败 | 回滚当前原子写入，保留此前提交 | 部分失败，可重试 | 留下半条正式结果 |
| Prompt injection | 当作普通文档内容，不执行 | 通常无需单独打扰用户 | 扩权或泄露系统信息 |

所有失败必须使用稳定 reason code；内部异常可以安全摘要，但密钥、请求头和不必要的完整文档不得进入日志或用户响应。

## 11. LLM 调用账本

每次真实模型调用至少记录：

- `review_run_id`、业务节点和调用序号；
- provider、model、SDK/适配器版本；
- Prompt 版本与哈希；
- 输入对象 ID、文档版本 ID、可见 chunk/page ID 与 coverage；
- 输出 schema 版本、接受/拒绝结果与 reason code；
- 工具名称、次数、成功/失败和拒收原因；
- 开始/结束时间、延迟、重试次数；
- 输入/输出 token、供应商报告的用量与可计算成本；
- 截止原因：完成、人工停止、预算、超时、工具上限或失败。

账本默认记录引用和范围，不默认复制完整敏感 Prompt/文档。需要调试原文时必须有受控开关、脱敏、保留期限和访问审计。

## 12. 测试与合并门禁

### 12.1 确定性单元测试

必须覆盖 schema、枚举、引用、版本、权限、状态复算、预算、超时、重试、恢复和审计。不得 mock 掉被测试的门禁。

### 12.2 模型边界合同测试

可以 mock 模型响应，但要用正常、缺字段、超长、错误枚举、恶意引用、越权 ID、重复工具调用和 Prompt injection 等输出攻击真实验证层。

### 12.3 保存的真实模型评测

使用版本化公开样本和人工标准答案，保存 provider、model、Prompt、数据集版本、结果、延迟和成本。至少评测：

- 资格/实质性要求召回；
- 评分项召回；
- 引用可打开率和相关性；
- 高风险漏项；
- 无证据通过次数；
- 企业事实编造次数；
- 失败与停止条件是否诚实。

### 12.4 端到端与真实业务验证

E2E 必须走文件版本、解析、Agent、门禁、人工决定、修改、新版本和复核链路。真实项目验证必须取得数据授权，并与公开样本评测分开记录。

### 12.5 合并规则

- 仅有 mock 测试，不能宣称真实模型质量；
- 仅有 live smoke，不能宣称业务准确率；
- Prompt/model/dataset 任何一项变化，都不能沿用未经复跑的质量结论；
- 出现一次“无证据已满足”、企业事实编造、跨项目取证或未披露的不完整核查，均阻止发布。

## 13. 分阶段开发顺序

在阶段划分之外，以下项目是第一次真实业务 Agent 调用前的不可跳过清单：

1. 建立持久化 `LLMCallRecord` / Tool 调用账本、Prompt 版本和稳定 reason code；
2. 建立统一 Coverage，记录模型实际看到与没有看到的范围；
3. 建立稳定 Evidence Fact / Claim 关系，不能继续只复制 quote；
4. 定义招标包、附件、补遗和澄清的组成与效力顺序；当前单一 tender 文档模型未扩展前，不得声称覆盖了完整招标包；
5. 建立项目选择 company evidence 的持久化授权关系；
6. 用服务端 `ReviewContext` 绑定 project、active versions、允许的资料和预算，不把这些 ID 交给模型自由选择；
7. 把超时、批大小、重试、token/费用上限和配置校验提前到真实调用之前；
8. 明确 Requirement 跨位置、跨版本的身份和指纹规则；
9. 在进入人工决定阶段前，为 Decision 增加操作者、所依据的版本/Assessment、状态和 superseded 关系，并区分可由人工声明的事实与必须上传书面证明的要求；
10. 规定 DocumentVersion、Requirement、Evidence、Assessment 和 Decision 的归档/删除策略，禁止级联删除悄悄抹掉证据链。

### 阶段 A：确定性地基与可观测性

完成并守住：版本化文件、可追溯解析、模型无关检索、严格结构对象、Evidence/Coverage/reason code、Prompt 版本、模型配置校验、调用账本、预算与恢复语义。

在这些基础未完成前，可以开发和测试局部候选能力，但不得宣称形成了可靠的端到端 Agent 核查。

### 阶段 B：受限要求提取与证据核查

按顺序实现：

1. 有引用门禁的 RequirementCandidate；
2. 有项目/版本范围的 EvidenceCandidate；
3. 有 unsupported-pass gate 的 AssessmentCandidate；
4. 服务端状态复算；
5. 待确认与 ActionItem；
6. 持久化、可恢复的有界 ReviewRun。

先用一个主 Agent。只有真实评测证明角色冲突无法通过 Prompt、工具和上下文边界解决时，才考虑多 Agent。

### 阶段 C：人工决定、版本闭环与质量证明

建立稳定的 Evidence → Assessment → Human Decision 关系；完成投标稿修改、版本差异、连带影响、增量复核和报告绑定。用公开标准答案集达到产品设计中的质量阈值，并保存每次评测证据。

### 阶段 D：受限 Evidence Workspace 与 RAG

只有阶段 A-C 稳定后，再建设多文档资料工作区、向量/混合检索、重排和更大范围的受限 RAG。RAG 只能改善候选发现，不能替代版本、引用、相关性、Coverage 和状态门禁。

### 阶段 E：外部系统与执行能力

CRM、OA、网盘、采购平台、发信、签章、审批、付款或自动提交均需要单独的 Constitution impact 审查、最小权限、幂等、预览、具名人工确认、撤销/补偿和完整审计。在此之前不得直接开发为自动执行能力。

## 14. 当前项目基线（2026-09-18）

截至本规范生效时：

- 项目骨架、领域状态、可追溯数据模型、项目 API、安全版本化上传和旧 SQLite 安全迁移已实现并通过确定性测试；
- PDF/DOCX 可追溯解析、模型无关检索、Agents SDK 提取/核查、后台任务、人工决定、增量复核、UI、报告和评测框架仍按实施计划逐步开发；
- 尚未调用 OpenAI API 证明真实模型业务质量；
- 当前是单用户、受信任的本地工作区，没有多租户认证与隔离；不得宣传为“每个用户只能访问自己的项目”的生产级权限系统；
- 不得把后续计划描述成当前已交付能力。

此节是状态快照，不改变前述规范；每完成一个阶段，应更新项目状态文档，而不是降低本规范的验收门槛。
