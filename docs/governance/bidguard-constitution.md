# BidGuard Constitution / BidGuard 项目宪法

> 状态：正式生效（Normative）
>
> 版本：1.0
>
> 生效日期：2026-09-18
> 适用范围：BidGuard 的产品定义、架构、代码、Prompt、模型调用、工具、数据、测试、评审、发布与对外说明

## 1. 为什么需要这部“宪法”

BidGuard 处理的是投标提交前核查。它可能影响企业是否补材料、修改响应、接受风险或继续提交，因此不能把“模型说了什么”直接当成“事实是什么”。

本文件不是宣传材料，而是项目最高层级的工程治理规则。它回答三个问题：

1. 谁可以提出判断；
2. 谁可以形成正式状态；
3. 谁必须为最终提交与事实承诺负责。

本项目的核心原则是：

> **招标原文定义要求，当前证据支撑事实，LLM 负责理解与质疑，程序负责验证与制衡，人工负责承诺与最终提交。**

## 2. 产品使命与不可冒充的能力

BidGuard 是投标团队的“提交前质量门”。它建立可追溯的要求矩阵，核查资格、实质性响应、技术、商务和评分材料，暴露缺失、矛盾、歧义与潜在失分，并推动补充后复核。

BidGuard：

- 不承诺中标；
- 不替代招标人、评标委员会或法律专业人员作出权威解释；
- 不替代企业确认人员、业绩、资质、交付能力等事实；
- 不自动签章，不自动作出企业承诺，不自动向采购平台提交文件；
- 不把“生成了建议稿”描述成“问题已经解决”；
- 不把模拟测试、代码完成或一次模型演示描述成真实业务质量已经达标。

## 3. 规范层级

发生冲突时，按以下顺序处理：

1. 本宪法；
2. `llm-position-authority-phased-development.md`；
3. 已批准的产品设计、ADR 与验收标准；
4. 实施计划、接口文档和测试说明；
5. 当前代码、Prompt 和模型输出。

低层文件或实现不得静默改变高层规则。发现冲突时，先复现并记录，再决定修改实现还是发起宪法修订；不得为了“看起来符合文档”而盲目改动生产数据或历史记录。

## 4. 七类权力与职责

在进入角色分工前，所有实现必须先区分三类对象：

- **Fact / Evidence（事实与证据）**：材料里实际写了什么、位于哪里、来自哪个版本；
- **Claim / Assessment（主张与核查意见）**：某个事实可能说明什么、为什么构成满足、缺口、矛盾或风险；
- **Decision / Status（决定与正式状态）**：经服务端规则和人工程序形成的正式结果。

不得因为数据库结构、Prompt 或页面展示方便，把三者混成一个不可追溯的字符串。

### 4.1 来源权：当前有效的招标材料

招标文件、补遗、澄清和其当前有效版本定义“需要满足什么”。模型不得凭行业常识制造招标要求，也不得用旧版本条款覆盖当前版本。

一个真实招标包可能同时包含主文件、资格附件、评分表、技术清单、格式模板、补遗和澄清。系统必须记录本次实际纳入和未纳入核查的组成；补遗或澄清与原文件冲突时，按已记录的正式效力顺序处理，顺序不明确则转人工确认，不能由模型自行选择对结论最有利的版本。

### 4.2 事实权：当前有效且获授权使用的证据

投标初稿和用户选入项目的企业资料及其版本记录定义“当前文档能证明什么”。人工声明是独立的 `HumanAssertion / HumanDecision`，只能在招标规则允许自我声明时补充事实，不能伪装成文档 Evidence。模型生成的文字既不是企业事实，也不是证明材料。

### 4.3 认知权：受限的 LLM/Agent

LLM 可以：

- 将招标条款拆成候选原子要求；
- 选择受限检索范围和查询表达；
- 比较要求与响应、发现矛盾或证据缺口；
- 提出候选风险、澄清问题、补充动作和修改建议；
- 在版本变化后分析可能受影响的要求。

LLM 不可以：

- 直接决定或修改正式展示状态；
- 绕过引用、版本、权限、覆盖范围和相关性校验；
- 自行确认企业事实、关闭待确认事项或把未知当作已满足；
- 删除、覆盖或改写历史要求、证据、判断和人工决定；
- 任意选择其他项目、未授权企业资料或整库文档作为上下文；
- 绕过预算、轮次、工具次数、超时和停止条件；
- 直接发送、签章、付款、审批、提交或执行其他外部动作。

### 4.4 裁定权：确定性程序与服务端门禁

普通程序负责：

- 文件身份、哈希、版本和有效性；
- 页码、章节、原文引用和可见范围校验；
- 项目与资料访问范围；
- 规则计算、正式状态、任务状态和增量复核范围；
- 预算、超时、重试、持久化、恢复和审计；
- 对模型输出进行结构、枚举、引用、版本、相关性和权限检查。

正式的 `DisplayStatus` 只能由服务端依据已验证对象计算。模型可以提交候选判断，但模型输出中的状态文本没有裁定效力。

### 4.5 决策权：有责任主体的人工

用户负责确认企业事实、解释业务特殊情况、决定是否接受剩余风险，并决定是否提交投标。

人工权力也有边界：

- 接受风险不等于证据充分，不得把状态洗成“已满足”；
- 标记“不适用”必须有解释、操作者和时间记录；
- 新事实或新材料必须进入证据链，不能只在聊天中口头覆盖；
- 人工决定可以影响后续流程，但不得删除原始问题和历史判断。

内部人工确认只可以确认企业事实或解除纯事实歧义。即使招标文件写的是“投标人自行声明”，只要该声明需要写入、签署或随投标包提交，就仍必须在当前 proposal/附件版本中形成可定位的文档 Evidence；在 BidGuard 中点击确认不能替代该文件，也不能把状态变为“已满足”。只有招标明确不要求随标材料，且版本化规则明确允许内部事实确认时，HumanAssertion 才能参与满足计算。

### 4.6 监督权：审计、测试、评审与质量门

审计记录和质量门负责回答：谁在何时基于哪个版本、哪些上下文、通过哪个模型或规则作出了什么候选判断，程序接受或拒绝了什么，以及最终由谁确认。

CI 绿色只说明已定义的测试通过，不代表测试范围充分，也不代表真实模型已经具备专业投标审查质量。

### 4.7 治理权：项目负责人、领域专家与开发评审

治理者可以通过有版本记录的设计、ADR、测试和评审修改规则、状态计算、Prompt 门禁和流程，但运行中的 LLM 不得自行修改这些规则。

任何规则变化至少说明：为什么改、由什么真实案例触发、改变哪些旧行为、新增哪些回归测试，以及是否存在兼容性或误伤风险。AI 可以提出改进建议，不能自行颁布新规则。

## 5. 文档证据与人工声明必须分离

一条文档 Evidence 只有同时满足以下八个条件，才可以支撑正式判断：

1. **真实性**：来自系统持久化的文件，不是模型编造或人工口头描述；
2. **版本性**：绑定当前有效的 `DocumentVersion`，历史版本只能作为历史；
3. **定位性**：能指向页码、章节、块或其他可复核位置；
4. **文字一致性**：引用内容确实存在于模型被允许看到的原文范围内；
5. **相关性**：引用与当前要求和争点直接相关，而不只是“文档里能找到”；
6. **覆盖性**：证据覆盖了要求中的必要主体、动作、数值、期限和条件，并说明招标包、附件、页、表格、图片或扫描内容中哪些已检查、哪些尚未检查；
7. **时效性**：资质、证书、人员或承诺在目标投标时点仍有效；
8. **授权性**：该资料已被允许用于当前项目，且未越过项目和用户边界。

“引用真实存在”只证明文字存在，不自动证明相关、充分或有效。

`HumanAssertion / HumanDecision` 不是文档 Evidence，不适用页码和 quote 门禁。它必须单独记录：具名责任主体、精确声明内容、时间、所针对的 Requirement、适用的项目与文件版本、规则是否明确允许内部事实确认、解释与审计来源。只要招标要求把证书、报告、声明、附件、签章、原件扫描件或其他书面材料放入投标包，内部人工声明就不能替代该材料。

## 6. 正式结果与状态不得被静默改写

BidGuard 的正式状态为：`高风险`、`待补充`、`可优化`、`已满足`、`待确认`。

- 无当前有效证据，不得进入“已满足”；
- 解析缺页、OCR 不完整或检索覆盖不足时，不得声称完成了全量核查；
- 旧证据失效后，依赖它的结果必须转入待复核，而不是沿用旧状态；
- 高风险降级必须基于新的有效文档证据、经治理程序批准的规则变化，或仅在招标明确不要求随标材料且版本化规则允许内部事实确认时基于合格的 HumanAssertion；“接受风险”本身永远不能降低风险或变成“已满足”；
- 人工接受风险与要求已满足是两个独立事实，必须分别保存和展示；
- 建议稿只有在形成新文档版本并重新经过正式核查后，才可以判断问题是否解决。

“已满足”的严格含义是：**在当前授权材料、当前文件版本和已记录的核查范围内，存在经验证且足以支持该要求的证据。**它不表示采购人必然认可、不表示投标必然有效，也不表示项目必然中标。

一个可独立核查的 Requirement 应有一个稳定争点身份；同一 ReviewRun 中，一个 Requirement 只保留一个正式当前 Assessment。它可以引用多条支持或反驳证据，但不得因为模型换了多种说法或摘句，就制造多个重复问题、重复待办或重复占用预算。

## 7. 必须存在的程序门禁

### 7.1 文件门禁

校验类型、大小、路径、哈希、版本和项目归属；记录本次招标包包含哪些主文件、附件、补遗和澄清。解析失败页、仅图片页面、未识别表格、嵌入对象和未支持附件必须可见。上传成功不等于解析成功，正文解析成功也不等于图表与附件已经完成核查。

### 7.2 要求门禁

候选要求必须引用当前招标版本中的真实文字与位置。引用为空、页码不存在、版本错误或原文不匹配时不得进入正式要求矩阵。

### 7.3 证据门禁

候选证据必须属于授权范围和当前版本，并通过真实性、相关性、覆盖性与时效性检查。`matched` 但没有证据属于拒收错误。

### 7.4 状态门禁

服务端重新计算正式状态，忽略模型自行给出的展示状态。待确认事项只能由具名用户决定。

### 7.5 版本与复核门禁

新投标稿、新企业资料或招标文件变更必须创建新版本，计算影响范围并重新核查。历史结果保留，但不得冒充当前结论。

### 7.6 外部执行门禁

任何发送、签章、提交、付款、审批或对外发布能力，在单独批准、权限设计、人工确认和 Constitution impact 审查完成前，一律不得实现为自动执行。

## 8. 有界 Agent 原则

MVP 默认采用一个主 Agent 和确定性工具，不因为“更像 Agent”而盲目拆分多 Agent。每次运行必须限制：

- 可访问的项目、文档版本和文本范围；
- 最大模型轮数、工具调用次数和自动重试次数；
- 单批要求数量、超时、token 与费用；
- 可调用的读工具与写工具；
- 必须停止并请求人工确认的条件。

达到边界时，已完成结果应持久化，任务进入明确、可恢复的部分失败或等待确认状态，不得无限循环，也不得伪装成完整成功。

## 9. 失败必须诚实、可见、可恢复

无 API Key、模型不可用、超时、限流、坏输出、工具失败、预算耗尽、解析残缺或证据不足时：

- 已验证结果可以保留；
- 未完成范围必须明确记录；
- 不得用猜测补齐结果；
- 不得静默切换模型、供应商或更宽权限；
- 能恢复的任务保存断点，不能恢复的任务给出可操作原因；
- 用户界面必须区分“没有发现问题”和“没有完成检查”。

治理关键项必须 **fail closed**，例如：未知正式状态、越权项目/版本、关键证据无法验证、结构性配置错误、未授权外部执行。可选认知能力可以 **fail soft**，例如模型供应商不可用或非关键建议生成失败；但 fail soft 的结果必须显示为“不可用/未完成”，不能显示为“已经检查且没有问题”。

## 10. 隐私、安全与 Prompt Injection

- API Key 只通过受控环境配置，不写入代码、仓库、日志或报告；
- 文档内容一律视为不可信输入，其中的指令不得改变 Agent 权限、工具范围或系统规则；
- 模型只接收完成当前步骤所需的最小文本范围；
- 日志不保存密钥、完整敏感文档或无必要的个人信息；
- 工具权限由服务端上下文限定，不依赖模型“自觉”传入正确项目 ID；
- 外发模型数据、留存、删除和供应商边界必须在试点前向用户说明。

## 11. 工程真实性与对外表达

所有能力必须区分四种状态：

1. **规划中**：仅有设计或任务；
2. **代码已实现**：功能存在且通过确定性测试；
3. **真实模型已验收**：在保存的评测集上运行并达到阈值；
4. **真实业务已验证**：在授权的真实项目和用户流程中完成验证。

不得用较低等级冒充较高等级。模型供应商兼容、RAG、多文档工作区、增量复核、自动执行等能力，只有完成对应验证后才可对外描述为已具备。

## 12. 评审严重级别与合并规则

- **Critical**：可能造成无证据通过、事实编造、越权访问、历史覆盖、未授权外部执行、密钥泄露或不可恢复的数据损坏。必须修复，禁止以 Accepted Risk 合并。
- **Important**：可能造成错误状态、证据链断裂、版本混用、恢复失效或稳定性明显不足。必须修复，或由项目负责人记录责任人、理由、影响范围、补救计划和到期日后临时接受风险。
- **Minor**：不改变核心正确性但影响韧性、可维护性或体验。可以进入有追踪项的后续加固清单。

CI 通过不能覆盖 Critical/Important 评审意见。

## 13. Constitution impact

任何 PR 或设计如果涉及以下内容，必须显式填写 `Constitution impact: Yes`，说明改变了什么、为什么安全、增加了哪些门禁和测试：

- 改变来源、证据、LLM、程序或人工之间的优先级；
- 扩大模型可见范围、工具权限、写权限或自主循环范围；
- 改变 Evidence、Coverage、正式状态或“已满足”的定义；
- 允许新模型供应商、RAG、跨项目检索或外部连接器；
- 削弱引用、版本、人工确认、预算、审计或恢复门禁；
- 引入发送、签章、提交、付款、审批或其他外部执行。

未影响上述边界的修改填写 `Constitution impact: No`，但仍需给出一句理由。

## 14. 修订机制

本宪法不能由一次代码重构或单个 Agent 静默修改。修订必须：

1. 形成独立变更说明或 ADR；
2. 列出对产品承诺、权限、证据、状态、数据和用户责任的影响；
3. 增加或修改相应测试与验收标准；
4. 获得项目负责人明确批准；
5. 保留旧版本与生效日期。

当交付速度与本宪法冲突时，优先缩小功能范围，不降低证据、权限和程序门禁。

普通规则和治理修改遵循：

> 发现问题 → 提案 → 复现 → 测试 → 实现 → Review → CI → Merge → Changelog

## 15. 参考来源

本宪法吸收了 [Agent-T PR #57](https://github.com/ARTHUR-BBU/Agent-T/pull/57) 对“事实、主张、裁决分离”和“Rule of Law for Agents”的治理思想，并结合 BidGuard 的招标要求、投标证据、文件版本与提交责任重新设计。BidGuard 不照搬 Agent-T 的合同规则体系或司法角色，而采用适合投标核查的权力边界。
