## 1. 先说结论

BidGuard 已经从“一个 Agent 产品想法”推进到“有项目边界、有版本化文件、有可定位证据、有模型治理门禁、能提取带引用要求的工程底座”。

这还不是完整的投标审核产品。当前已经证明的是：

- 文件和版本可以被安全保存；
- PDF/DOCX 可以生成带位置和覆盖状态的解析结果；
- 检索可以限制在正确项目和授权版本内；
- OpenAI 与 EasyRouter 可以显式接入，但不会静默切换；
- Agent 只能在服务端给定的上下文和预算内运行；
- 要求候选必须引用真实、可定位的招标原文；
- 成功和失败的模型调用都可以留下安全台账。

尚未证明的是：真实模型在真实招标材料上的业务提取质量、完整招标包覆盖、投标响应核查质量和可直接提交投标。

## 3. 各任务的作用与类比

### Task 1：可运行工程骨架

Task 1 建立 FastAPI 后端、React/TypeScript 前端、配置、健康检查、开发脚本和基础 README。

它像给工地通水、通电、修道路。它还不是产品功能，却让后续代码拥有稳定的落脚点，并且让开发环境可以重复启动和验证。

已确认提交：`84aa8f5`、`ca55ebd`、`fe40077`。

### Task 2：领域状态与确定性规则

Task 2 统一了要求类型、证据状态、严重程度和展示状态，并把正式状态计算放到确定性程序中。

它像医院先统一“高风险、待复查、已确认”等病历词汇，避免后端、前端和模型各自发明含义。它确保模型可以提出候选意见，但不能自由决定正式展示状态。

已确认提交：`9159eb5`、`f4704ce`。

### Task 3：可追溯持久化模型

Task 3 建立项目、文档、版本、chunk、Requirement、ReviewRun、Assessment、EvidenceLink 和审计对象之间的关系，并补上外键、唯一性和批量写入保护。

它像档案馆给每份材料建立档案号和借阅记录。系统未来必须能回答“这条结论基于哪一版文件和哪条证据”，Task 3 就是这个能力的数据库基础。

已确认提交：`10845ef`、`d0c8ea4`、`d88c715`、`bb1d1a2`。

### Task 4：项目与企业资料 API

Task 4 建立项目身份、项目列表、截止日期和状态统计，并明确项目与企业资料的边界。

它像给每个客户建立独立档案柜。没有项目边界，系统无法可靠判断某份企业资质是否可以用于当前投标，也无法阻止不同项目之间的资料串用。

已确认提交：`5bc0749`、`8c7ecf3`、`67595ad`、`741c10f`。

### Task 5：安全、版本化文件上传

Task 5 实现 PDF/DOCX 类型限制、大小限制、内容哈希、安全存储路径、重复文件去重、版本递增和旧 SQLite 安全迁移。

它像档案馆接收材料时盖章、编号、验真，并保留每一版历史。后面的解析、检索和 Agent 引用，必须建立在这个稳定的文件版本上。

已确认提交：`32d7ab6`、`868a328`、`c804d02`。

### Task 6：保留位置的 PDF/DOCX 解析

Task 6 把文件变成带页码、章节、chunk 和 Coverage 的证据材料。解析失败、扫描页、复杂表格、图片和附件不会被静默当成“已检查”。

它像把厚招标书拆成带门牌号的档案盒。后续如果不能指出“第几页、哪一段”，就不能形成可靠审核链。

当前限制包括 OCR、复杂表格几何、嵌入附件和 DOCX 非正文故事内容；这些限制会进入 Coverage，而不是被隐藏。

### Task 7：模型无关证据检索

Task 7 用确定性词法检索从解析片段中找候选证据，并在服务端验证项目、版本、角色和 Coverage。

它像律师助理先从几百页卷宗中找出可能相关的页码，但不直接宣布案件结论。检索结果仍是候选证据，不是正式 EvidenceLink，也不是“已满足”。

### Task 8：模型供应商与 Agents SDK 通道

Task 8 建立了 OpenAI 主通道和 EasyRouter 显式备用通道。供应商、模型名、超时、重试和 smoke 行为集中管理；不支持的配置 fail closed，不自动切换。

EasyRouter 的 `deepseek-v4-flash` 已完成无业务文本的连通性 smoke。这个结果只证明“通道能通”，不证明模型具备投标审核质量。

### Task 8A：LLM 治理门禁

Task 8A 建立 `ReviewContext`、Coverage、`LLMCallRecord`、企业资料授权、招标包成员、冲突阻断和运行预算。

它像档案室门禁：模型只能看当前项目、当前版本、明确授权的资料和规定范围，并且每次调用都留下安全账本。预算、轮次、工具、超时和失败语义由服务端掌握。

这是进入真实业务文本调用前的强制门槛。

### Task 9：带引用的原子要求提取

Task 9 的程序化部分实现了：

- 无工具、结构化输出的单一提取 Agent；
- 当前项目/当前招标版本的引用门禁；
- 页码、章节和 quote 存在性校验；
- excerpt 与授权 chunk 的原文绑定；
- Requirement 保存、重复检测和历史保留；
- 业务指纹与引用位置指纹分离；
- 成功、超时、供应商异常和坏输出的调用台账。

它像审标团队里的“拆单员”：把复合条款拆成可以逐条检查的要求，但不判断企业是否合规，也不生成正式风险状态。

Task 9 的 Step 1—5 和 Step 7 已完成；Step 6 的真实单文件模型评测尚未执行。

## 4. 当前架构的核心判断

BidGuard 采用的不是“把所有材料交给模型”的路线，而是：

```text
原始文件
 → 确定性版本和解析
 → 项目范围内检索
 → 服务端 ReviewContext
 → 受限 Agent 候选
 → 引用/版本/权限门禁
 → 正式持久化
 → 人工确认和后续审核
```

模型是理解与质疑能力，不是权限系统、数据库、事实裁判或提交责任主体。
