# BidGuard Task 13 阶段复盘：把“待确认”接成人的决定，再按变化范围复核

> 文档性质：开发记录与能力边界说明，不是营销承诺。
>
> 复盘范围：Task 13「人工决定、行动项与增量复核」。
>
> 当前基线：功能已合并到 `main`；287 个后端测试通过，Ruff 与 Mypy 通过。

## 1. 先给结论

Task 12 让审核任务可以后台持续执行，但遇到不确定性时只能停在 `awaiting_confirmation`。Task 13 补上了“人负责决定”和“材料变了只复核受影响范围”这两个缺口。

现在系统可以记录 `confirm`、`deny`、`not_applicable` 三类人工决定，要求责任人和解释；行动项可以被具名完成；proposal、company evidence 或 tender 版本变化时，服务端会计算受影响的 Requirement，失效旧 Assessment，并把必要范围交回 Task 12 Worker。

这不是让人工点击直接改写合规结论，而是把人的责任、材料版本和后续复核正式接回证据链。

## 2. 为什么必须有 Task 13

Task 12 像一名有值班表的审核员：它能继续工作，也能在不确定时停下来。但如果没有人工决定台，任务会永远停在“请确认”；如果文件更新后仍沿用旧判断，审核结果就会像拿着旧版合同去签新版合同。

Task 13 建立两套闭环：

```text
不确定性 → 人工决定 → 审计记录 → 后续行动/复核

新文件版本 → 影响范围计算 → 失效旧结论 → 只重审必要要求
```

## 3. 它在整体开发地图中的位置

```text
Task 11：按规则运行审核 Agent
        ↓
Task 12：任务可排队、可恢复、可查状态
        ↓
Task 13：人工决定 + 行动项 + 版本影响复核  ← 本次
        ↓
Task 14：前端把这条闭环做成工作台
```

Task 13 是从“系统能发现问题”走向“团队能负责地处理问题”的连接层。

## 4. 本次真正落地的能力

### 4.1 人工决定是追加历史，不是覆盖历史

每条决定保存：

- `confirm`、`deny` 或 `not_applicable`；
- 必填解释；
- 责任人；
- 创建时间；
- 对应 Requirement、Assessment、ReviewRun 和版本 ID；
- `human_decision_recorded` 审计事件。

已有决定不能通过新决定被覆盖，Requirement 有决定历史后也不能被物理删除，只能停用并保留历史。

### 4.2 Agent 的待确认事项也进入正式记录

Agent 请求人工确认时，会创建 `pending` Decision 和审计事件。它只是“等待人处理”的记录，不是人工决定，也不是证据。人处理后追加正式决定，原始待确认记录仍然存在。

### 4.3 行动项完成不等于问题自动解决

用户可以完成补材料、修改响应或核验事实的行动项。系统保存完成者和完成时间，但不会因为点击“完成”就直接把状态改成 `satisfied`。如果需要证明，仍然要上传新版本材料并重新核查。

### 4.4 增量复核按证据依赖计算

- 新 proposal 版本会影响引用同一 proposal 文档历史版本的 Assessment；
- company evidence 版本变化会影响引用该证据版本的 Assessment；
- 新 tender 版本会让旧 Requirement 矩阵退出当前范围，但保留历史；
- 未受影响的 Requirement 保持当前 Assessment；
- 受影响 Assessment 标记为非当前，旧 EvidenceLink 不再作为当前结论依据；
- `re-review` 会先把受影响 Requirement ID 写入 ReviewRun，再创建 queued ReviewJob。

服务端计算最低影响集合，不能由模型为了省调用而缩小范围。

## 5. 用户实际得到什么

```text
Agent 发现证据不足
    ↓
用户确认 / 否决 / 标记不适用
    ↓
系统保存责任人与解释
    ↓
用户完成行动项或上传新版本
    ↓
系统找出受影响要求
    ↓
Worker 只重新核查必要部分
```

这让审核结果开始具备“当前有效”语义，而不是一张永远不变的静态表。

## 6. 验收证据

- Task 13 专项测试：8 项通过，覆盖决定合同、行动项 API、历史保护、proposal 增量影响和 tender 矩阵失效；
- 后端全量测试：287 项通过；
- Ruff：通过；
- Mypy：44 个源文件无问题；
- 新增字段通过旧 SQLite 安全迁移路径；
- GitHub `main` 已开启 PR、禁止强推和禁止删除保护。

## 7. 仍然没有完成的内容

- 没有多租户身份系统；当前操作者标识来自受信任本地工作区；
- 没有自动修改投标文件、自动上传、签章或提交；
- 人工决定不能替代招标要求必须提交的书面材料；
- 没有真实业务语料上的准确率、召回率和成本验收；
- 没有完整前端任务工作台和报告导出。

## 8. 下一步因果链

Task 13 让后端闭环成立，但用户还没有一个清晰的页面去查看任务阶段、当前 Assessment、待确认事项、行动项和复核结果。因此下一步进入 Task 14：建立类型化前端 API 客户端和应用壳层，把后端已经验证过的状态原样呈现给用户，不在前端重新发明业务规则。
